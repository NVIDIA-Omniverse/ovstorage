**Ordinary cloud URLs resolve automatically for `s3` and `azure` connections.**
When an `s3` or `azure` connection registers below an `alias` layer, hidden alias rules for the common URL spellings of the same data are generated from the connection's own configuration — the six public AWS shapes (virtual-hosted and path-style, including the legacy `s3-<region>` form and the China partition suffix), the exact configured shape for explicit-endpoint profiles (MinIO, B2, R2, custom), and Azure's blob endpoint (plus the DFS endpoint under `hierarchical_namespace`). A user pasting `https://bucket.s3.us-west-2.amazonaws.com/…` gets the object without translating it to `s3://bucket/…` first. Generated rules are hidden (addressable, never advertised — listings keep showing the canonical form only), regenerate at registration rather than persisting, are withdrawn with their connection, and are marked with `org.omniverse.ovstorage/alias-derived-from` in `list_connections` output; an explicit alias rule on the same prefix evicts the generated one (until the connection re-registers), and a `suppressed` visibility override turns a single spelling off reversibly. Authorization is untouched: policy evaluates the caller-supplied address before alias resolution and no grant is ever generated, so in gated deployments the generated aliases do nothing until their URL space is granted. A broader `suppressed` override covers the generated spellings beneath it, so a generated rule never re-opens a subtree an operator denied above it.

**`s3` signs China-partition requests against `amazonaws.com.cn`.** An `s3` connection in a `cn-` region derives its canonical host on the China partition suffix, so an anonymous (public-bucket) read reaches the real endpoint. Requests made through the AWS SDK were already correct; this is the path that builds the host itself, and it is the path a pasted `.com.cn` URL lands on once the alias rules above accept it.
