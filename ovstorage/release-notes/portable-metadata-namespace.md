**The reserved `user_metadata` namespace is now `ovstorage_` and the attribution key is `ovstorage_modified_by`, so attributed writes land on Azure.** Through a broker or REST host running the default `user_metadata` attribution strategy, every write and every metadata update to an Azure branch failed with Azure's `InvalidMetadata`: Azure metadata names must be C# identifiers, and the previous hyphenated key `ovstorage-modified-by` was not one. The respelled key is a valid name on every backend, so an attributed write succeeds on Azure and the host reads the stamp back as `modified_by`.

The release also pins down which metadata keys are portable. A key of lowercase ASCII letters, digits and underscores that does not start with a digit, matching `[a-z_][a-z0-9_]*`, is accepted by every backend that stores user metadata. A backend may accept a wider set of names, but a caller must not assume a name outside that subset travels across routes: backends differ in the characters they take and in whether they preserve case. Size and count limits remain backend-specific. The plugin conformance guide, `docs/public/plugin-storage/CONFORMANCE.md`, states the guarantee for plugin authors.

This is a clean break with no compatibility path for the previous spelling. An object stamped under `ovstorage-modified-by` by an earlier release is no longer harvested into `modified_by`; on every backend that key surfaces as ordinary `user_metadata`, carrying the writer's principal id, which is often email-like. A deployment that wants those objects scrubbed can remove the key with `update_metadata`; the next attributed write stamps the new key regardless. A third-party plugin that spells the key itself, through the constants `ovstorage-plugin` exports, picks up the new spelling when rebuilt against this release. This release is at Layer plugin ABI 19, so a plugin built against ABI 18 is refused at load and cannot run against this release until it is rebuilt. That refusal covers the respelling as well as the layout change ABI 19 carries: a plugin that re-asserts attribution on a continued write has to move in lockstep with an attributing host, because a skewed one would strip and re-stamp only the previous namespace, letting a client-supplied `ovstorage_modified_by` in the continuation survive as the attested writer. The move also runs in the other direction: an earlier release did not reserve `ovstorage_modified_by`, so a client could store it as ordinary metadata, and an attributing host on this release harvests that stored value as the attested writer. Before enabling an attributing host, scrub client-writable `ovstorage_*` keys from existing objects with the same one-off `update_metadata` pass; until that runs, `modified_by` on pre-upgrade objects is caller-controlled rather than host-vouched.

The per-operation annotation, `WriteOptions.message`, is stored under the user-metadata key `x_ov_message` on every backend that stashes it as user metadata. Previously the key was `x-ov-message`, which Azure refused as an invalid metadata name, so any Azure write or metadata update carrying a message failed with `InvalidMetadata`. An annotation recorded by an earlier release keeps the previous key and reads back as ordinary `user_metadata`. S3 records it on its streaming and presigned write paths as well as on a buffered write; the built-in `file` backend stores no user metadata and drops the annotation, as its own note in this release says. The respelled key sits outside the reserved `ovstorage_` namespace, so an attributing host leaves it visible rather than stripping or harvesting it. When a call supplies both `message` and its own `x_ov_message` entry, the caller's entry stands and the message is dropped, because caller metadata is persisted while the annotation is droppable by contract.
